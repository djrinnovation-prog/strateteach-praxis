דף החלטה (Decision Record) · טיוטה לאישור הבעלים

תאריך: 2026‑07‑16 בעלים: דן · רפי · יואב סטטוס: טיוטה — ממתין לחתימת 3 הבעלים

1ההחלטה (סיכום מנהלים)

  • מערכת אחת, בבעלות מלאה של הבעלים. לא מפצלים לשתי פלטפורמות. כל הליבה — אסטרטגיה, UX, וגם הביצוע — יושבת תחת בעלות אחת ו‑governance אחד.
  • בידוד‑הביצוע נשמר בתוך המערכת. כסף נסחר רק דרך שירות‑ביצוע מבודד (signed message → queue → worker → Vault), אף פעם לא ממפתחות שמוחזקים בדפדפן. זה העיקרון היחיד שאסור לוותר עליו.
  • ממשק גישה שכבתי מסודר (4 שכבות, מטריצת הרשאות ברורה).
  • מודול ניהול‑בעלים + שכבת השקעת‑בעלים: קרן משותפת אחת, חלוקה יחסית, אישור ביצוע 3‑מ‑3 (פה אחד).

2עקרונות‑על (Non‑negotiable)

  1. הפרדה מוחלטת בין כספי‑לקוחות לכספי‑בעלים — חשבונות, רשומות, דוחות ו‑P&L נפרדים לגמרי. אף פעם לא מתערבבים.
  2. אין מסלול ביצוע ישיר מהדפדפן. מפתחות‑בורסה חיים רק ב‑Vault צד‑שרת. הפרונט לא מחזיק מפתחות ולא קורא ל‑create_order.
  3. כל ביצוע על הון‑הבעלים דורש אישור 3‑מ‑3 מפורש. אין ביצוע אוטונומי, אין עקיפה.
  4. Kill‑switch + audit מלא + גבולות (per‑order cap, daily cap) + הפרדת סביבות (testnet → mainnet, gated).
  5. mainnet/כסף‑אמיתי חסום עד שכל שערי‑הבטיחות + שאלות ה‑provenance/רישוי נסגרים בכתב.

4מודול ניהול‑בעלים (שכבה 3)

הרחבה של פורטל הבעלים הקיים (/owners):

  • כספי‑חברה (הכנסות, הוצאות, budget) — owner‑only.
  • Governance / הצבעות — החלטות, אישורים, יומן‑החלטות (Decision Log פנימי).
  • ניהול תפקידים — הענקת/שינוי גישה (הפאנל הקיים).
  • דוחות — עסקי + השקעה.

5שכבת השקעת‑הבעלים — הקרן המשותפת

  • מבנה: קרן אחת משותפת (דן+רפי+יואב). לא חשבון נפרד לכל אחד.
  • בעלות יחסית: ledger של הפקדות לכל בעל → אחוז‑בעלות יחסי בקרן. NAV משותף; לכל בעל מוצג חלקו היחסי.
  • הפקדות/משיכות: מתועדות ומבוקרות (מי, כמה, מתי). משיכה = פעולה מבוקרת (לא כאן בטיוטה — נסגור מדיניות בהמשך).
  • ביצוע על הון‑הקרן (arm/trade): פה אחד, 3‑מ‑3. הזרימה:
    הצעת‑פעולה → 3 אישורים מפורשים → חלון‑זמן → ביצוע דרך שירות‑הביצוע המבודד → audit + התאמה (reconciliation).
    ללא 3 אישורים — שום דבר לא זז.
  • דוחות: ביצועים, חלוקה, P&L של הקרן, וחלק יחסי לכל בעל.
  • הפרדה: מנותק לחלוטין מכספי‑לקוחות ומ‑AutoPilots‑הדמו (שנשארים סימולציה).
  • owner‑only — כולל מול אורן: הקרן המשותפת, השקעות‑הבעלים וכל תנועותיהן (הפקדות, משיכות, מסחר על הון‑הבעלים, חלוקה/NAV, אישורי ה‑3‑מ‑3) גלויות לשלושת הבעלים בלבד. אורן מנהל את המכונה הפיננסית (שכבה 2א) אך ההון הפרטי של הבעלים ותנועותיו חסומים ממנו.

6ארכיטקטורת הביצוע הבטוחה (המנוע שמאחורי הכול)

הדפוס (מוכח, כפי שראינו ב‑Praxis — כאן בבעלותכם):

פרונט (בלי מפתחות)  →  הודעה חתומה (HMAC)  →  תור (queue)  →  worker  →  מפתחות מ‑Vault  →  בורסה
                                                                   ↑
                                       sizing/caps בצד‑שרת · kill‑switch · audit · reconciliation
  • Envelope‑only: הפרונט/הסיגנל שולח כוונה (signal + action), לא כמות, לא מפתחות. הכמות מחושבת בצד‑שרת מה‑config.
  • מקור הקוד — 2 דרכים (החלטת בעלים, §8): (א) להביא את עבודת‑הביצוע של Praxis תחת בעלותכם (IP assignment — שומר את ההקשחה שכבר נבדקה ב‑testnet) · (ב) לבנות in‑house לפי אותו דפוס (Praxis = שרטוט‑ייחוס). מומלץ (א) אם ה‑IP ניתן להעברה — זול ובטוח יותר מ‑rewrite.

8פתוח / דורש חתימת/החלטת בעלים

  1. IP של Praxis — assignment לחברה (מועדף) או build in‑house. עין של עו״ד (ראז) על ההקצאה בכתב.
  2. provenance + רישוי של המנוע/אסטרטגיות (שאלות S1–S7) — חסם מסחרי אמיתי, לא ניתן לעקוף עם ארכיטקטורה.
  3. מדיניות הפקדה/משיכה מהקרן המשותפת (מי מאשר משיכה, חלון‑זמן).
  4. אישור סופי לפני כל מעבר ל‑mainnet/כסף‑אמיתי.

9הצעד המיידי

Phase 0 — להפוך את StrateTeach ל‑advisory ולנתב כל ביצוע לשירות המבודד, עם הגייט החי כבוי. שינוי קטן, תשואת‑בטיחות עצומה, ובלי סיכון לכסף. ממתין לאישורכם כדי להתחיל.

מסמך זה הוא טיוטה לאישור. אינו מבצע שום פעולה, אינו מזיז כסף, ואינו מפעיל mainnet. כל ביצוע נשאר תחת אישור מפורש שלכם.
